# Keeper — Autonomous Bill Payment Simulation & Agent Security Guardrails

Keeper is a secure, autonomous bill-payment simulation designed for older adults. It demonstrates how an AI agent can assist with routine recurring expenses while strictly enforcing boundaries that prevent unauthorized beneficiaries, excessive payments, prompt-injection manipulation, and unsafe autonomous bank transfers.

> **CRITICAL NOTICE**: **All payments in Keeper are simulated.** No real money is ever moved, and no live payment networks or bank accounts are accessed.

---

## 1. System Architecture & Trust Boundaries

Keeper implements an asymmetric, defense-in-depth architecture across **7 distinct trust boundaries**:

```text
┌─────────────────────────────────────────────────────────────┐
│                    Frontend (React 19)                      │
│               TanStack Start / Router / Vite                │
└──────────────┬──────────────────────────────▲───────────────┘
  Human Actions│                              │ REST API Responses
  (JWT Auth)   ▼                              │
┌──────────────────────────────┐              │
│     Keeper REST API          │              │
│     FastAPI (/api/v1)        │              │
└──────────────┬───────────────┘              │
               │                              │
               │ (Approval resume / query)    │
               ▼                              │
┌──────────────────────────────┐              │
│       Untrusted Agent        │              │
│    (MCP Tool Proposer)       │              │
└──────────────┬───────────────┘              │
               │ propose_payment              │
               ▼                              │
┌──────────────────────────────┐              │
│   ArmorIQ v2 Gateway Proxy   │              │
│   (armoriq-sdk==0.6.10)      │              │
└──────────────┬───────────────┘              │
               │ Intent-Authorized Tool Call  │
               ▼                              │
┌──────────────────────────────┐              │
│     Keeper MCP Endpoint      │              │
│    (/mcp - Bearer Secret)    │              │
└──────────────┬───────────────┘              │
               │                              │
               ▼                              │
┌───────────────────────────────────────────┐ │
│       Keeper Authoritative Policy         │ │
│   - Verified Beneficiaries Only           │ │
│   - Household Payment Limit (e.g. ₹10k)   │ │
│   - Exact-Detail Approval Hash Match      │ │
└──────────────────────┬────────────────────┘ │
                       │ Authoritative Exec   │
                       ▼                      │
┌───────────────────────────────────────────┐ │
│   Mock Bank API + Ledger (SQLite)          │ │
│      Inside Keeper Backend Process         │─┘
└──────────────────────┬────────────────────┘
                       │ Read-Only Verification
                       ▼
┌───────────────────────────────────────────┐
│            Independent Witness            │
│         Confirmed Paid / Absence         │
└───────────────────────────────────────────┘
```

1. **Untrusted Agent**: Proposes actions. Exposes zero tools that can execute payments directly or bypass policies.
2. **ArmorIQ Proxy**: Enforces agent intent validation via signed intent plans and 60-second intent tokens.
3. **MCP Endpoint Security**: Requires the ArmorIQ bearer credential and a short-lived HMAC household context generated by the authenticated backend.
4. **Keeper Policy Engine**: Authoritative validator for approved beneficiaries, trusted billers, and spending limits.
5. **Human In The Loop**: Mandatory for payments exceeding policy thresholds. Exact cryptographic detail hashing (`details_hash`) guarantees no parameters are altered between approval and execution.
6. **Payment Execution & Mock Bank Ledger**: Single protected execution path. The mock bank API and its independent SQLite ledger run inside the Keeper backend process and enforce idempotent `client_reference` deduplication.
7. **Independent Witness**: Queries the mock bank's ledger directly in read-only mode to produce tamper-evident verification reports.

## 2. Technology Stack

- **Backend**: Python 3.11, FastAPI, Pydantic v2, SQLAlchemy 2.0, psycopg 3, httpx, PyJWT, pytest.
- **Agent Security**: `armoriq-sdk==0.6.10` verified against Python 3.11.
- **Mock Bank**: FastAPI routes embedded in the Keeper backend, with a SQLite ledger.
- **Database**: Supabase PostgreSQL is the application source of truth. SQLite is limited to isolated tests or explicit local-only mode.
- **Frontend**: React 19, TanStack Start & Router, Vite 8, Radix UI, Tailwind CSS.

## 3. Getting Started

### 3.1 Backend Virtual Environment Setup

**Windows PowerShell:**
```powershell
cd backend
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -e ".[dev]"
```

*Note: If PowerShell execution policy restricts script execution, run tools directly:*
```powershell
.\backend\.venv\Scripts\python.exe -m pip install --upgrade pip
.\backend\.venv\Scripts\python.exe -m pip install -e backend
```

**macOS / Linux:**
```bash
cd backend
python3.11 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e ".[dev]"
```

### 3.2 Environment Variables

Create `backend/.env` from `backend/.env.example`:

```bash
cp backend/.env.example backend/.env
```

Required backend configuration:
- `SUPABASE_DB_URL`: Supabase PostgreSQL connection string. The API refuses to start without it.
- `SUPABASE_JWT_SECRET`: Verifies Supabase JWT signatures; unsigned tokens are rejected.
- `MOCK_BANK_AUTH_TOKEN`: Private bearer token protecting the backend's internal mock-bank routes.
- `ARMORIQ_ENFORCEMENT=required` and `ARMORIQ_ROUTE=proxy`; unsupported modes fail closed.
- `ARMORIQ_API_KEY`, `KEEPER_MCP_PUBLIC_URL` (public HTTPS URL ending in `/mcp`), and `KEEPER_MCP_INBOUND_SECRET` for ArmorIQ.
- `GEMINI_API_KEY`: Backend-only Gemini credential. Keep it and all service credentials out of `frontend/.env`.

### 3.3 Initialize Supabase

With `SUPABASE_DB_URL` configured in `backend/.env`, run the repeatable migrations and seed once:

```powershell
cd backend
.\.venv\Scripts\python.exe scripts\setup_supabase.py
```

The command inserts only missing seed rows. The API checks migration version 4 at startup.

### 3.4 Running the Services

Start the Keeper backend once; the mock bank is part of this process and is not a separate service:
```powershell
cd backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
```

Start the frontend separately:
```powershell
cd frontend
npm install
npm run dev
```

The frontend will be available at `http://localhost:3000`. Check backend health at `http://127.0.0.1:8000/health`. Set `VITE_API_BASE_URL=http://127.0.0.1:8000` in `frontend/.env` if running on non-default ports.

## 4. Supabase Database Setup

`backend/scripts/setup_supabase.py` applies four versioned SQL changes and idempotent seed rows. It creates household, policy, biller, beneficiary, bill, approval, attempt, event, Witness, and bill-document schema. Seeded bills remain pending; payment and Witness outcomes are never fabricated. Existing records are not overwritten. API startup verifies migration version 4 and never runs `create_all` against Supabase.

## 5. ArmorIQ v2 Integration & MCP Server

### Verified SDK APIs
Run the verification script:
```powershell
.\backend\.venv\Scripts\python.exe backend/scripts/verify_armoriq_sdk.py
```
This checks the installed `armoriq-sdk==0.6.10` constructor and method signatures. The SDK uses the ArmorIQ-hosted proxy endpoint; `KEEPER_MCP_PUBLIC_URL` is Keeper's registered MCP URL, not the SDK proxy URL.

After deploying `/mcp` behind public HTTPS and setting the ArmorIQ environment variables, register from the repository root:

```powershell
.\backend\.venv\Scripts\Activate.ps1
.\backend\scripts\armoriq_register.ps1
```

The script invokes `armoriq validate`, `armoriq register`, and `armoriq status`. A local SDK test does not prove external registration or active policy.

### MCP Server (`keeper-payments`)
Exposes strictly **4 read/propose tools**:
1. `list_bills`
2. `get_bill`
3. `propose_payment`
4. `get_payment_status`

Execution tools (`execute_payment`), beneficiary additions, and policy modifications are never exposed to agents.

### Enforced Payment Path
Only required ArmorIQ proxy mode can execute tools. Gemini can request exactly four registered tools; an ArmorIQ hold persists as `needs_review`, a denial stays blocked, and unavailable configuration stops before bank execution. Keeper independently enforces trusted beneficiaries, exact human approval, and hard limits. The mock bank requires `MOCK_BANK_AUTH_TOKEN` and idempotent references.

Approving a bill starts background processing and never marks it paid synchronously. The approval view polls persisted status. Retry is available only for `needs_review` with no existing payment attempt; ambiguous attempts must be reconciled first. PDF/JPEG/PNG uploads (5 MB maximum) store the original bytes and SHA-256 in Supabase. Amount and payee details remain explicitly user-entered and validated rather than inferred from untrusted document text.

## 6. Testing

Execute automated backend tests:
```powershell
.\backend\.venv\Scripts\pytest.exe -v backend/tests
```

- **Backend Invariant Tests**: Health, auth, household isolation, beneficiary denial, approval resumption, uploads, reconciliation, and idempotency.
- **ArmorIQ Offline Tests (U1–U11)**: Plan capture, token minting, policy denials, expiry, ambiguous timeouts, cross-household prevention.
- **ArmorIQ Live Tests (L1–L8)**: Run against real ArmorIQ service when live credentials and public MCP URL are provided.
